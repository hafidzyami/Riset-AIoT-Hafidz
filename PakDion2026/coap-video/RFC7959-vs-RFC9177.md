# RFC 7959 vs RFC 9177 for live video over CoAP

This is the protocol-level companion to the implementation in `src/`. It
explains *why* the two block-wise mechanisms behave differently, then states
what to expect from the measurements in `results/`.

---

## 1. Why video needs block-wise transfer at all

CoAP runs over UDP and a CoAP message is meant to fit in a single datagram —
ideally inside one link MTU so that IP fragmentation never happens. RFC 7252
§4.6 effectively caps a useful payload at around 1024 bytes.

A single MJPEG frame from the Pi camera is far larger than that:

| capture | typical frame | blocks at 1024 B |
|---|---|---|
| 640×480 | ~7–16 kB | 7–16 |
| 1280×720 | ~22 kB | 22 |
| 1920×1080 | ~65 kB | 64 |

So every frame *must* be fragmented at the CoAP layer. The only question is
which fragmentation mechanism carries it — and that choice dominates the
achievable frame rate.

## 2. RFC 7959 — Block-Wise Transfers (2016)

### Options

| option | no. | class | carries |
|---|---|---|---|
| `Block1` | 27 | critical | payload of a **request** (PUT/POST/FETCH body) |
| `Block2` | 23 | critical | payload of a **response** (GET body) |
| `Size1` | 60 | elective | total request-body size hint (from RFC 7252, reused here) |
| `Size2` | 28 | elective | total response-body size hint |

The option value packs **NUM** (block index), **M** (more-blocks flag) and
**SZX** (size exponent). Block size is `2^(SZX+4)`, so SZX 0…6 gives 16…1024
bytes; SZX 7 is reserved.

### Operation: strictly lock-step

Fetching an *N*-block body with `Block2` is *N* separate confirmable
request/response exchanges:

```
CON GET /cam/frame  (Block2: NUM=0, M=0, SZX=6)   ──►
                                                  ◄──  ACK 2.05 (Block2: 0/M=1/6) + 1024 B
CON GET /cam/frame  (Block2: NUM=1, M=0, SZX=6)   ──►
                                                  ◄──  ACK 2.05 (Block2: 1/M=1/6) + 1024 B
                             ⋮                                        ⋮
CON GET /cam/frame  (Block2: NUM=N-1, M=0, SZX=6) ──►
                                                  ◄──  ACK 2.05 (Block2: N-1/M=0/6) + tail
```

Two consequences follow directly, and they are the whole story:

1. **Transfer time ≈ N × RTT.** The effective window is exactly *one block*, so
   throughput is capped at `block_size / RTT` no matter how much bandwidth is
   free. This is a bandwidth-delay-product failure: on our ~10 ms link a 64-block
   1080p frame cannot beat ~1.5 fps however fast the WiFi is.
2. **Wire cost ≈ 2N datagrams**, because every block needs its own request.

### Reliability

RFC 7959 adds no reliability of its own — it inherits CoAP's confirmable
retransmission (RFC 7252 §4.2): `ACK_TIMEOUT` 2 s, `ACK_RANDOM_FACTOR` 1.5,
`MAX_RETRANSMIT` 4, with exponential backoff. Congestion control is the
implicit `NSTART = 1`: one message outstanding at a time.

The sting is that **one lost block stalls the entire transfer for at least
2 seconds**, because the next block is never requested until the current one
resolves. Loss does not degrade a 7959 transfer gracefully; it serialises
2-second penalties onto the critical path.

RFC 9177 §1 states the problem plainly: block-wise transfer is a poor fit for
bulk data because of exactly this per-block round trip.

## 3. RFC 9177 — Block-Wise Transfer Supporting Robust Transmission (2022)

### Options

| option | no. | carries |
|---|---|---|
| `Q-Block1` | 19 | payload of a **request** |
| `Q-Block2` | 31 | payload of a **response** |

The NUM/M/SZX encoding is deliberately identical to RFC 7959, so the *framing*
is familiar. Like `Block1`/`Block2`, these are **critical** options: a server
that does not implement RFC 9177 must reject the request with `4.02 Bad Option`
rather than ignore the option. The practical difference from RFC 7959 is not
the option class but **deployment** — every CoAP stack speaks Block2, far fewer
speak Q-Block2 — which is why a client has to probe before using it (see §5).

### Operation: burst, then repair

Q-Block is built around **non-confirmable (NON)** messages. The sender does not
wait for per-block acknowledgement; it streams the body out and lets the
receiver report what went missing:

```
NON GET /cam/frame  (Q-Block2: NUM=0, M=0, SZX=6)  ──►
                                                   ◄──  NON 2.05 (Q-Block2: 0/M=1/6) + 1024 B
                                                   ◄──  NON 2.05 (Q-Block2: 1/M=1/6) + 1024 B
                                                   ◄──  NON 2.05 (Q-Block2: 2/M=1/6) + 1024 B
                                                        ⋮  (up to MAX_PAYLOADS)
                                                   ◄──  NON 2.05 (Q-Block2: N-1/M=0/6) + tail
```

One request, *N* responses. If blocks 3 and 7 are lost, the client asks for
just those two rather than restarting or stalling.

### Recovery machinery

| element | role |
|---|---|
| `4.08 Request Entity Incomplete` | receiver of a **Q-Block1** body reports missing blocks |
| `2.31 Continue` | sender may continue after a partial body is acknowledged |
| `application/missing-blocks+cbor-seq` (Content-Format **272**) | CBOR sequence listing the missing block numbers |
| multiple `Q-Block2` options in one request | client re-requests exactly the blocks it lacks |
| `M` bit on a recovery `Q-Block2` | shorthand for "this block **and everything after it**", so a lost tail costs one request |

This is *selective repair*: cost is proportional to what was actually lost, not
to the size of the body.

### Transmission parameters (RFC 9177 §6.2)

Because NON messages carry no acknowledgement, RFC 9177 has to supply its own
pacing and its own congestion control. It does so with new parameters:

| parameter | default | meaning |
|---|---|---|
| `MAX_PAYLOADS` | 10 | payloads that may be sent back-to-back before pausing |
| `NON_TIMEOUT` | 2 s | pause after a `MAX_PAYLOADS` burst |
| `NON_TIMEOUT_RANDOM` | — | `NON_TIMEOUT × ACK_RANDOM_FACTOR` |
| `NON_RECEIVE_TIMEOUT` | 4 s | how long a receiver waits before asking for missing blocks (must be ≥ `NON_TIMEOUT_RANDOM` + 1 s) |
| `NON_MAX_RETRANSMIT` | 4 | how many times the receiver may ask again |
| `NON_PROBING_WAIT` | — | bounds capability probing |
| `NON_PARTIAL_TIMEOUT` | 247 s | how long a partially received body is retained |

**`MAX_PAYLOADS` is the congestion window.** It is what replaces the per-block
ACK of RFC 7959: instead of one block in flight, up to `MAX_PAYLOADS` may be,
and the sender must then pause for `NON_TIMEOUT` unless it hears something.
Raising it trades burst tolerance for throughput; both binaries expose it as
`--max-payloads` so the trade-off is measurable rather than theoretical.

## 4. Side-by-side

| | **RFC 7959** | **RFC 9177** |
|---|---|---|
| Options | Block1 (27), Block2 (23) | Q-Block1 (19), Q-Block2 (31) |
| Option class | critical | critical |
| Deployment | universal | **needs RFC 9177 on both ends** |
| Message type | confirmable (CON) | non-confirmable (NON) |
| Blocks in flight | **1** | up to `MAX_PAYLOADS` (10) |
| Round trips for *N* blocks | **N** | **1** (+ repairs) |
| Datagrams for *N* blocks | ≈ **2N** | ≈ **N + 1** |
| Time for *N* blocks | ≈ N × RTT | ≈ N × serialisation, RTT paid once |
| Throughput ceiling | `block_size / RTT` | link bandwidth |
| Loss of one block | stalls whole transfer ≥ `ACK_TIMEOUT` (2 s) | that block re-requested; rest already delivered |
| Recovery granularity | per block, serialised | **selective, batched** (missing-blocks CBOR / M bit) |
| Congestion control | implicit `NSTART=1` | explicit `MAX_PAYLOADS` + `NON_TIMEOUT` |
| Best for | config, firmware, occasional large reads | **bulk / streaming / telemetry** |

## 5. Capability negotiation, and why it matters here

Because Q-Block1/Q-Block2 are critical options, a client cannot simply use them
against an unknown server. libcoap handles this with block-mode flags, which
both of our binaries expose:

| flag | effect |
|---|---|
| `COAP_BLOCK_USE_LIBCOAP` | let libcoap drive the block state machine |
| `COAP_BLOCK_SINGLE_BODY` | deliver a reassembled body to the application |
| `COAP_BLOCK_TRY_Q_BLOCK` | offer Q-Block; **fall back to RFC 7959** on `4.02` |
| `COAP_BLOCK_USE_M_Q_BLOCK` | use the M bit when repairing Q-Block2 |
| `COAP_BLOCK_FORCE_Q_BLOCK` | skip probing entirely (`--force-q-block`) |

The probe costs one exchange on the first request only. Our client discards
`--warmup` transfers before recording, so the probe never pollutes the numbers.

## 6. What this means for live video specifically

Three properties of video interact with the choice of mechanism:

**Frames are large and deadline-bound.** A frame that arrives after the next
one was captured is worthless. RFC 7959's `N × RTT` cost turns a 1080p frame
into ~64 serialised round trips, which is a fixed latency floor that no amount
of bandwidth removes. RFC 9177 pays the RTT once.

**MJPEG makes loss independent per frame.** Every frame is a self-contained
JPEG, so a block lost in frame *k* damages only frame *k* — there is no GOP to
corrupt. That is what makes this a clean testbed: the loss experiment measures
the *recovery mechanism*, not codec error propagation. (With H.264 a lost block
would poison every dependent frame, which confounds the comparison — hence
MJPEG.)

**The sender is the constrained device.** The Pi 4 builds and parses one PDU
per block. RFC 7959's 2N datagrams versus RFC 9177's N+1 is therefore not just
a wire-efficiency argument but a CPU and energy argument on the camera node.

### Predictions

1. Latency should drop by roughly the round-trip factor, growing with frame
   size — smallest at 640×480, largest at 1080p.
2. Datagrams per frame should fall from ≈2N to ≈N+1, i.e. towards a factor of 2.
3. Client transmissions should fall by close to *N*, since one request replaces
   N.
4. Server CPU should fall roughly with the PDU count.
5. Under loss, RFC 7959 should degrade sharply (2 s stall per lost block on the
   critical path) while RFC 9177 degrades gradually.
6. Smaller blocks should hurt RFC 7959 much more than RFC 9177, because they
   multiply the number of round trips rather than just the number of datagrams.

### What actually happened

Predictions 1–4 and 6 held, and closely:

| prediction | outcome |
|---|---|
| 1. latency drops by ~the round-trip factor | held — 2.4×, 2.6×, 2.5× at 480p/720p/1080p |
| 2. datagrams/frame fall from ≈2N toward ≈N+1 | held — 1.73×–1.82×, matching the model to within a few percent |
| 3. client transmissions fall by ~N | held — 7.5×–9.8× |
| 4. server CPU falls with PDU count | held — 2.1×–3.6× |
| 6. small blocks hurt RFC 7959 more | held — the advantage grows from 2.37× at 1024 B to 2.70× at 128 B |

**Prediction 5 was wrong**, and it is the most interesting thing the experiment
produced. RFC 7959 does degrade sharply under loss — but so does RFC 9177, and
for the same underlying reason: *both mechanisms become timer-bound, not
structure-bound, the moment packets start disappearing.* At 2 % loss both fall
by roughly 30×, to about 1 fps.

The reason is that a live video frame has a ~33 ms budget while both recovery
timers are measured in **seconds**:

- RFC 7959 stalls `ACK_TIMEOUT` = 2 s, and pays it *per lost block, serially*;
- RFC 9177 waits `NON_RECEIVE_TIMEOUT` = **4 s** — twice as long — but then
  repairs *all* missing blocks in a single request.

So the mechanism named for "robust transmission" ships with a default recovery
timer twice as long as the one it improves on. Its batching is what lets it
stay ahead anyway at every loss level measured (1.2×–4×), and at 20 % loss it
still delivers 25 of 30 frames where RFC 7959 delivers **one**.

The practical conclusion is that **RFC 9177's defaults are tuned for bulk
telemetry, not for video**, and that `NON_RECEIVE_TIMEOUT` is the parameter to
reach for. Experiment E5 tests exactly that.

`results/report.md` holds the measured outcome, and §"Results" of the README
summarises it.

## 7. Practical recommendations

For live video over CoAP on constrained hardware, in priority order:

1. **Use the largest block size the path allows** (1024 B). This is the single
   cheapest win and it helps RFC 7959 most, because block size divides the
   number of round trips. Going from 128 B to 1024 B is worth ~6.7× on
   RFC 7959 and ~5.9× on RFC 9177.

2. **Prefer RFC 9177 where both ends support it.** On a clean link it buys
   ~2.2–2.6× frame rate and ~2.5× lower latency, cuts datagrams per frame by
   ~1.8×, cuts client transmissions by ~9×, and halves-to-thirds the sender's
   CPU — the last of which matters most on a battery-powered camera.

3. **Do not leave `NON_RECEIVE_TIMEOUT` at its default.** This turned out to
   matter *more than the choice of mechanism*: at 5 % loss, lowering it from
   4.0 s to 1.2 s was worth 3.7× over RFC 9177's own defaults and 8.1× over
   RFC 7959. Remember RFC 9177 §6.2 couples the two timers —
   `NON_RECEIVE_TIMEOUT ≥ 1.5 × NON_TIMEOUT + 1` — so `NON_TIMEOUT` must come
   down with it. The rationale for the loose defaults is bulk telemetry, where
   a 4-second repair delay is invisible; for 15 fps video it is ~60 frame
   times.

4. **Scale `MAX_PAYLOADS` with the body.** It is a congestion window measured
   in payloads, so a body needing far more blocks than `MAX_PAYLOADS` is paced
   by `NON_TIMEOUT` pauses rather than by the link (experiment E4).

5. **Keep RFC 7959 as the fallback.** Q-Block is a critical option and is not
   universally implemented; `COAP_BLOCK_TRY_Q_BLOCK` gives the RFC 9177 path
   when available and degrades to RFC 7959 when not, at the cost of one probe
   exchange on the first request.

## 8. Honest limitations

- **RFC 9177 is not a free win.** It trades CoAP's per-message reliability for
  throughput. RFC 9177 §3 restricts its applicability to networks where the
  traffic is provisioned or otherwise congestion-managed — it is not intended
  for the open Internet, and `MAX_PAYLOADS` is the knob that keeps a burst from
  behaving antisocially.
- **Both ends must implement it.** RFC 7959 is universal; Q-Block is not.
- **This testbed uses one client.** The interesting congestion-control
  behaviour of `MAX_PAYLOADS` appears with many senders sharing a bottleneck,
  which is future work (§Future work in the README).
- **Loss is emulated in userspace** by libcoap's own packet-loss facility, so it
  is Bernoulli (independent) loss on the server's transmit path. Real wireless
  loss is bursty and correlated; `tc netem` with a Gilbert-Elliott model would
  be the next refinement, and needs root on the camera node.
- **No DTLS.** libcoap is built without DTLS here so the measurement isolates
  block-wise behaviour. Both RFCs are expected to be used with DTLS or OSCORE
  in production, which adds per-datagram overhead that would *widen* the gap
  (RFC 9177 sends fewer datagrams).
